# Video demo script

Target length: 6–8 minutes. Record the browser with the live app open. Use the sample request IDs below so the results match the supplied dataset. All people and locations shown are synthetic.

## Before recording

1. Open https://nurse-patient-match.streamlit.app/ in a fresh browser tab.
2. Set browser zoom to 90–100% and use a desktop-sized window.
3. Close unrelated tabs or notifications. Wait for each page to finish loading before speaking.
4. Keep this file nearby as a checklist. Do not describe the demo data as real patient or nurse records.

## 1. Introduction and purpose — 30 seconds

**Show:** Find a Nurse page with the default request.

**Say:**

"This is the Nurse Match Engine. It takes a home-care request, first checks which nurses meet the essential requirements, and then ranks only those eligible nurses. The aim is to make the shortlist easier to understand: each result has a score, a reason and a breakdown of how that score was calculated. This is an academic prototype using synthetic data, not a live healthcare service."

## 2. Continuity and score explanation — 60 seconds

**Select:** `R001 — Radha Pereira`.

**Show:** The top-five list, previous-nurse summary, then open Asha Nair's details.

**Say:**

"This request is for post-surgery care, Hindi, and weekday night shifts in Delhi. Thirty-five of the 200 sample nurses pass the hard rules. Asha Nair is ranked first. The request says nurse N065 has cared for this patient before, and N065 is Asha, so the continuity factor contributes its full weight. This is why she can rank above a closer nurse."

"The score is not generated by an AI text model. Each factor is converted to a value between zero and one, multiplied by its weight, and added together. The table shows those contributions, so the displayed score can be checked."

## 3. A previous nurse who fails a hard rule — 45 seconds

**Select:** `R018 — Shweta Chauhan`.

**Show:** Previous nurse KPI and the warning/reason on the results page.

**Say:**

"This request also has a previous nurse, N103. However, N103 does not speak Urdu, which is a required language for this request. The engine does not let continuity override a hard requirement. The previous nurse is therefore marked as not eligible, and four other nurses remain. This is an important distinction: familiarity can improve a score, but it cannot make an ineligible nurse eligible."

## 4. Care skill and language requirements — 35 seconds

**Select:** `R061 — Savita Bhosale`.

**Show:** Request summary and eligibility funnel.

**Say:**

"Here the family needs dementia care and Punjabi, for weekday night shifts in Delhi. The engine filters the pool by care skill, language and availability, in that order. Five nurses pass all three checks. The funnel makes the filtering visible instead of hiding it inside a single score."

## 5. Distance is normally a score, not a hard rule — 60 seconds

**Select:** `R004 — Deepa Joshi`.

**Show:** Top-five list and map with the travel-radius toggle off. Point out the nurses based in Mumbai near the bottom of the list. Then open Scoring options, enable the travel radius and set it to 25 km. Press Find Top Matches.

**Say:**

"This request is for baby care in Pune. With the radius turned off, distance affects ranking but does not automatically exclude a nurse. That is why nurses from Mumbai can still appear when they meet the care, language and availability requirements. Their distance lowers their score."

"When I enable a 25-kilometre radius, distance becomes an additional hard rule. The list now contains only three nurses. This shows the trade-off: a strict service area can reduce long-distance recommendations, but it can also leave fewer choices."

## 6. Small result lists and no-match cases — 55 seconds

**Select:** `R080 — Rohit Shinde`, with the radius turned off.

**Say:**

"This request has the smallest eligible pool in the standard sample dataset: three nurses. The engine returns the three that qualify rather than inventing two more results or treating the shorter list as an error."

**Then select:** `R030 — Geeta Singh`. Enable the 25 km radius at 25 km and submit.

**Say:**

"Here, six nurses pass the normal skill, language and availability checks, but none is within 25 kilometres. The result is an explicit no-match state. The funnel shows where the candidates were removed, and the interface suggests changing the radius or request constraints."

**Optional second example:** Select `R092 — Amit Mehta` with the 25 km radius still enabled. It also produces no eligible nurses.

## 7. Input safeguards — 30 seconds

**Show:** Scoring options on any request. Set all four manual weights to zero while the learned-weight option is off, then submit.

**Say:**

"The scoring controls also have a basic safeguard. If all four weights are zero, there is no meaningful ranking to calculate, so the app asks for at least one positive weight rather than silently returning a misleading score."

Restore a valid weight setting before moving on. This is a UI validation example; it does not change the stored sample dataset.

## 8. Fairness Analytics — 60 seconds

**Open:** Fairness Analytics.

**Show:** Workload balancing slider at 0.10, KPI cards, comparison table and chart. If time permits, move the slider to 0.00 and back to 0.10.

**Say:**

"This page evaluates how recommendations are distributed across nurses when all 100 sample requests are processed. The Gini value summarises concentration: zero would mean an even distribution, while a higher value means first picks are concentrated among fewer nurses. The page compares normal score ranking with a simulated workload penalty for nurses who have already been ranked first."

"In this seeded run, the Gini value moves from 0.83 to 0.78 at a balancing weight of 0.10. The busiest nurse's share falls from 8% to 5%, while the average score of the first pick changes from 0.555 to 0.552. This is a small trade-off between match score and distribution."

"This is not a demographic fairness audit. The dataset has no real people or demographic labels, and the metric measures recommendation distribution, not actual assignments or patient outcomes. It is an initial academic analysis, not proof that a real deployment is fair."

## 9. Learned Weights — 65 seconds

**Open:** Learned Weights.

**Show:** Hand-set, hidden preference and learned columns; success-rate cards; learning curve.

**Say:**

"The default weights are hand-set design choices. This page demonstrates one possible way to estimate them from feedback. Since this project cannot use real feedback, it creates simulated past matches and outcomes using an invented set of hidden preferences. A logistic regression is fitted to the simulated outcomes, and its coefficients are normalised to become the learned weights."

"The chart compares the hand-set weights, the hidden preferences used by the simulator, and the learned values. On 100 held-out sample requests, this run gives 60.7% expected success with hand-set weights, 64.6% with learned weights and 64.7% using the simulator's hidden preferences. These numbers only show that the method can recover the rule used to generate the synthetic feedback. They are not measured patient satisfaction."

"Importantly, clicking Find Top Matches does not record a real outcome or update these weights. No personal feedback is stored on this device. The learning experiment is generated by the code with fixed seeds, and the displayed report is repeatable."

## 10. Close with limits — 25 seconds

**Show:** Return to Find a Nurse.

**Say:**

"The main limitations are that the data is synthetic, distance is straight-line rather than travel time, availability is a repeating weekly pattern, and the engine does not model nurse capacity or current caseload. The prototype demonstrates transparent filtering, ranking, explanations and evaluation. A real service would need validated data, operational rules, privacy safeguards and human review before use."

## Claims to avoid in the recording

- Do not say that the app learns from the user's searches or stores feedback. It does not.
- Do not call the synthetic success percentages real satisfaction or accuracy measurements.
- Do not call the fairness page a demographic bias audit. It measures the distribution of first-ranked recommendations.
- Do not describe straight-line distance as driving distance or travel time.
- Do not present a high match score as a clinical judgement or guarantee of care quality.
